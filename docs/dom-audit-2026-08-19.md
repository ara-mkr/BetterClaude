# claude.ai DOM audit — 2026-08-19

Live inspection of the shipped claude.ai app, run before any injection code was
touched. Machine-readable companion: `docs/dom-audit-2026-08-19.json`
(regenerate with `npm run audit:dom`).

**Method.** `scripts/audit-claude-dom.js` opens the real site in the app's own
persisted Electron session (`persist:betterclaude`) with a preload that surveys
structure and runs the shipping `core/layout-probe.js` against the same live
page. A second pass drove the *running* dev build over the Chrome DevTools
Protocol (`--remote-debugging-port`) to measure BetterClaude's injected chrome
against Claude's, since the first pass deliberately loads the site with no
injection at all.

**Redaction.** Developer-authored identifiers (`data-testid`, class tokens,
ids, roles) are recorded verbatim — they are the things the adapter must key
off. Anything that could be user content (text nodes, `aria-label` values) is
allowlist-filtered in the renderer and reduced to `<redacted:N>` unless every
word is UI chrome. No conversation, project, or account content appears in this
file or in the JSON.

Routes audited: `/new` (signed in), `/projects`, `/code`.
Viewports: 1440×872 (audit window), 1804×951 (live dev build).

### 2a. The `<nav>` fallback now resolves to *our own* chrome

`core/layout-probe.js`'s sidebar region falls back to `document.querySelector("nav")`.
On the live build there is **exactly one `<nav>` in the document, and it is
BetterClaude's own settings-panel nav** (`nav.bc-sp-nav`, 0×0 while the panel
is closed). Measured in the running app:

```
navs: [ { cls: ["bc-sp-nav"], rect: 0×0, parent: DIV,
          html: '<nav class="bc-sp-nav"><button class="bc-sp-nav-item" …' } ]
```

So the fallback does not merely miss — it returns a confidently wrong answer
pointing at BetterClaude's own DOM, and only *sometimes*, depending on whether
the settings panel has been constructed yet. A miss is recoverable; a wrong
answer that looks like a hit is not. **Any target resolver must exclude
BetterClaude-owned nodes at every tier.**

## 3. The Home / Code tab bar

It is **not** a top-level app bar. It lives inside the sidebar, as the first
child of `[data-testid="sidebar"]`:

```
div[role="group"].df-pills[data-segmented][data-pills="2"][data-chorus-callout]
    rect 8,44 272×32                     (viewport 8,90 with the 46px title bar)
├── div.df-pill-indicator[data-at][data-snap]        (sliding active-pill highlight)
├── button.df-pill[data-mode="cowork"][aria-label="Home"]   9,45 136×30
└── button.df-pill[data-mode="code"]  [aria-label="Code"] 145,45 133×30
```

Facts that matter for building against it:

* **No ARIA tab semantics at all.** No `[role="tablist"]`, no `[role="tab"]`,
  no `aria-selected`. `core/layout-probe.js`'s `findTopTabBar()` therefore
  returns `null` — correctly, since there is no top-level tab bar; the control
  it is looking for does not exist in that position.
* **Active state** is `data-active` + `aria-current="page"` on the active pill.
  Navigating to `/code` moves both to the `data-mode="code"` pill.
* **Element ids are React-generated** (`_r_b_`, `_r_e_` on `/new`; `_r_9_`,
  `_r_c_` on `/code`). They change per route. Never key off them.
* **`data-mode`, `data-segmented`, `data-pills` are the durable hooks.**
* **Icons are a private-use-area icon font rendered inside the label element.**
  `button.textContent` is `"Home"`, not `"Home"`. An exact-match text
  heuristic that skips PUA stripping silently finds nothing — this bit the
  audit script itself on its first run.

### Is the native Code tab Anthropic's, or a slot we can use? — **Anthropic's. Reserved.**

Resolved by navigating to it and auditing what loads. `/code` is a full
Anthropic-owned product surface with its own testids:

```
code-prompt-input   code-prompt-send   code-sidebar-feedback-button
epitaxy-env-pill    pending-nav-frame  pending-nav-body  pending-nav-shield
```

The pill is a routed mode switch inside Anthropic's own state machine
(`cowork` ↔ `code`), driving a real feature. It is not an empty slot.
**Step 2 must add an adjacent BetterClaude-owned control, not hijack this one.**

## 5. Injected-chrome reconciliation (live dev build, 1804×951)

Measured with BetterClaude actually running:

| | |
|---|---|
| `#betterclaude-titlebar` | `0,0 1804×46` ✅ |
| `body > #root` | `0,46 1804×905`, `transform: matrix(1,0,0,1,0,46)`, class `bc-claude-root` ✅ |
| `aside[aria-label="Sidebar"]` | `0,46 288×905` ✅ nothing under the bar |
| Home/Code pills | `8,90 272×32` ✅ fully visible and clickable |

The geometry compensation is **working**. Two real defects, both from
over-broad or stale selectors rather than from the new tab bar:

1. **`SELECTORS.chatHeader` is the bare tag selector `header`.** It paints
   `background: rgb(13,2,33)` onto whatever `<header>` the page has. On chat
   routes that header spans the content column and reads as intentional; on
   `/code` it is an 840px band floating mid-canvas
   (`header.epitaxy-composer-width`, measured `630,87 840×59`) and renders as a
   stray purple slab across the top of the Code surface.

2. **The signed-in/signed-out discriminator is wrong on `/code`.**
   `syncContextualChrome()` infers signed-out from the absence of
   `[data-testid="chat-input"]`. `/code` is a signed-in route with no composer,
   so `body` gains `bc-signed-out`, which:
   * switches to the signed-out geometry branch (`body padding-top: 0`, root
     `translateY(46px)`, `overflow: visible` — the root loses its clip
     boundary);
   * unmounts InteractionFX and disables the companion on a route where the
     user is very much signed in.

   Measured on `/code`: `bodyClasses: [… "bc-signed-out", "bc-layout-recognized"]`.
   The `recognized` there is also false confidence — with `signedOut` inferred,
   `absenceIsNormal` suppresses the genuine `sidebar` miss.

## 6. claude.ai's own update / reload prompt — NOT CAPTURED

21 structural candidates on `/new` and 14 on `/code` matched the container
shapes an update banner would plausibly use (`[role="status"]`, `[aria-live]`,
`[class*="toast"]`, `[class*="banner"]`), but **every one had
`matchesCopy: false`** — none carried refresh/reload/restart/new-version copy.
No update was pending during the audit window, and one cannot be forced.

**Unresolved.** Consequence for Step 4, stated explicitly because it changes
the design: recovery must not depend on detecting the banner. Re-injection
hangs off `did-finish-load` / `dom-ready`, which fire whether or not we
recognised what caused the reload. Detection is logging only, and it logs what
it saw so the real markup gets captured the first time a user hits one.

## 7. Durable hooks, ranked

Use, in order: `data-testid` → ARIA role + `aria-label` → semantic tag →
stable `data-*` (`data-mode`, `data-segmented`) → structural geometry →
normalised text. Never: React ids (`_r_*`, `base-ui-*`), Tailwind utility
classes, positional indexes ("the second pill is Code").

Verbatim testids observed: `chat-input`, `chat-input-attach`, `chat-input-send`,
`file-upload`, `model-selector-dropdown`, `sidebar`, `sidebar-recents`,
`sidebar-projects`, `sidebar-pinned`, `sidebar-rows-skeleton`,
`user-menu-button`, `page-header`, `project-cell-pin`, `code-prompt-input`,
`code-prompt-send`, `code-sidebar-feedback-button`, `epitaxy-env-pill`,
`pending-nav-frame`, `pending-nav-body`, `pending-nav-shield`.

`[data-testid="user-menu-button"]` is present on **every** signed-in route
including `/code`, which makes it the correct signed-in discriminator — the job
`[data-testid="chat-input"]` was wrongly doing.
